2. Verification correction: avoiding a false pass

A first attempt to test the old Git commit was launched while the current directory was this repository. Python places the current directory at the beginning of sys.path, so import pyDataverse loaded the fixed local package instead of the separately installed old commit. That run succeeded, but it was an invalid pre-fix test and was discarded.

Incorrect isolation

cwd = /Users/shihuayu/Documents/GitHub/pyDataverse
import pyDataverse
# Resolves ./pyDataverse before site-packages.
# A supposed “old commit” test actually exercises new local code.

Observed false result: constructor passed with 18 blocks.

Correct isolation

cwd = /private/tmp
print(inspect.getfile(pyDataverse))
# .../site-packages/pyDataverse/__init__.py

Running outside the repository and printing the imported file proved that the old installed package was used. The original exception then reproduced exactly.

Reusable verification rule: when comparing an installed baseline against an uncommitted working tree, run the baseline outside the repository and always print inspect.getfile(package). Otherwise import-path shadowing can create a false success.

4.2 Added a single loop-aware bridge

New file: pyDataverse/api/utilities/async_run.py. The common script path stays on standard-library asyncio.run. A synchronous call made while an event loop is already active is moved to a single worker thread where a fresh event loop can safely run the coroutine. 

from __future__ import annotations

import asyncio
from concurrent.futures import ThreadPoolExecutor
from typing import Any, Coroutine, TypeVar

T = TypeVar("T")
_EXECUTOR = ThreadPoolExecutor(max_workers=1, thread_name_prefix="pyDataverse-async")


def run_async(coro: "Coroutine[Any, Any, T]") -> T:
    try:
        asyncio.get_running_loop()
    except RuntimeError:
        return asyncio.run(coro)

    return _EXECUTOR.submit(asyncio.run, coro).result()

8. Scope and residual notes

  • Issue #240 itself is verified fixed. The constructor exception and both sync-to-async execution branches are covered on the exact reported Python release.
  • The full repository suite was not run locally. tests/conftest.py requires a live Dataverse plus valid API_TOKEN and API_TOKEN_SUPERUSER. This verification is now complete in GitHub Actions, which supplied those values through gdcc/dataverse-action for every Python 3.10–3.14 job.
  • The complete issue example goes beyond this exception. This report verifies construction and metadata initialization—the exact failing portion of the reported traceback. Dataset upload behavior requires an appropriate collection and credentials and is a separate concern.
  • Worker serialization is intentional. Calls made from an active loop share one worker and run serially. The current pyDataverse coroutine bodies create their event-loop-bound HTTP clients inside the coroutine, so resource creation, use, and cleanup stay on the worker loop.
  • No upstream pull request or release has occurred. The branch is committed and pushed to the authenticated user's fork; upstream review remains a separate next step.
